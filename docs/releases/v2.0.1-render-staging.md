# Deploy FinReview 2.0.1 to a separate Render account

**Staging only. Not stable release or public broker activation.**

## Separation

The existing Render workspace attached to ChatGPT is not the alternative Render account requested for staging. Do not import this Blueprint into an account holding the live `main` production service. It explicitly pins both staging services to GitHub branch `release/2.0.1` and disables automatic redeployment.

The Blueprint `render.staging.yaml` prepares:
- A separate Docker/FastAPI web service using the existing root Dockerfile.
- A separate static frontend built with `STAGING_API_URL` to target the new backend.
- Broker OAuth, direct market API, probes and Telegram dispatch all **disabled** by default.

**Database:** Provision a **separate** staging PostgreSQL instance and enter its connection URL as `DATABASE_URL` during Blueprint setup. The Blueprint deliberately does not provision a paid DB or reuse any production DB. Test migration and rollback with disposable test records only. Never copy production customer data.

## Account-side steps

1. Log in to the other Render account and connect GitHub access to `sathishkannan-labs/myfinreview`. Verify you are not in the current production workspace.
2. Choose New > Blueprint, repository `sathishkannan-labs/myfinreview`, branch `release/2.0.1`, Blueprint path `render.staging.yaml`.
3. Review the Render plan/cost before accepting creation (the YAML has no paid plan selection). Confirm no existing production service or database appears in the proposed resource plan.
4. Create staging PostgreSQL separately and supply its URL to `DATABASE_URL`; set `CORS_ALLOW_ORIGINS` to the exact generated staging frontend HTTPS origin.
5. Set `STAGING_API_URL` to the newly created backend's HTTPS `*.onrender.com` origin. Trigger or redeploy the frontend build to bake the correct URL into `config.runtime.js`.
6. Generate independent `FINREVIEW_BROKER_VAULT_KEY` and `FINREVIEW_BROKER_IDENTITY_HMAC_KEY` server-side. Never share them, insert them in frontend builds, commit them to Git or reuse production secrets. Keep broker OAuth disabled until private staging access controls and log redaction are validated.
7. Confirm the backend responds at `/`, frontend loads `/index.html`, login and portfolio regression checks pass with staging-only accounts, and authenticated research features show expected states.
8. Only after confirming protected staging access and provider-approved callbacks, follow `docs/releases/v2.0.1-live-test-readiness.md` for read-only broker smoke checks.

**Privacy limitation:** Render static sites and ordinary web services have public URLs unless additional access control is implemented. A separate account is an *isolation boundary*, not an authentication/privacy guarantee. Do not place real broker tokens in an unprotected staging service.

**Release gate:** Successful deployment alone is insufficient to publish `v2.0.1` stable; tests, data licensing, security review, live broker entitlement verification and user acceptance remain mandatory.
